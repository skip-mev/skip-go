<Info>
The fields and logic discussed in this guide pertain to the JSON response object from the `/v2/tx/status` endpoint of the Skip Go API. Refer to the [API Reference](/api-reference/prod/transaction/get-v2txstatus) for detailed schema information.
</Info>

This guide explains how to read the `/v2/tx/status` response to tell whether a transaction, and each transfer step in it, is in progress, successful, or failed. You can use it to drive progress indicators, status messages, and error displays in your application.

## Response Structure

The response has a `transfers` array with one entry for each transaction the user signed. Most routes need only one transaction, so `transfers` usually has one entry. Apply the logic below to each entry.

| Field | Description |
|---|---|
| `state` | Status of the whole transaction. |
| `transfer_sequence` | The transfer steps in the transaction, in order. |
| `next_blocking_transfer.transfer_sequence_index` | Index in `transfer_sequence` of the step that is in progress or caused the failure. Usually `null` once the transaction has finished. |
| `transfer_asset_release` | Where the user's assets ended up. See [Asset Release](#understanding-asset-release-transfer_asset_release). |

The top-level `transfer_sequence` and `status` fields are deprecated, so don't use them.

## Transaction Status

| `state` | Meaning |
|---|---|
| `STATE_COMPLETED_SUCCESS` | The entire transaction finished successfully. |
| `STATE_COMPLETED_ERROR` | The transaction finished, but an error occurred. |
| `STATE_PENDING_ERROR` | An error occurred, and the transaction is still settling (for example, funds are returning to the source chain). Treat it as failed. |
| `STATE_ABANDONED` | Tracking stopped because the transaction did not progress within the time limit. |
| Any other value | The transaction is still in progress. |

## Step Status

For each step in `transfer_sequence`, compare its index with `next_blocking_transfer.transfer_sequence_index` (the blocking index below).

| Step status | When |
|---|---|
| Success | The transaction `state` is `STATE_COMPLETED_SUCCESS`, or the step comes before the blocking index. |
| Pending | The step is at the blocking index and the transaction is still in progress. |
| Failed | The transaction `state` is `STATE_COMPLETED_ERROR`, `STATE_PENDING_ERROR`, or `STATE_ABANDONED` and the step is at the blocking index. If the `state` is `STATE_COMPLETED_ERROR` and there is no blocking index, treat the last step as failed. |
| Not started | The step comes after the blocking index. |

<Note>
When the `state` is `STATE_COMPLETED_ERROR` or `STATE_PENDING_ERROR`, `next_blocking_transfer` may be `null`. To find the step that failed, check the error fields of each step, such as `ibc_transfer.packet_txs.error`, `axelar_transfer.error`, or `error_tx` in `stargate_transfer.txs` and `layer_zero_transfer.txs`.
</Note>

## Example Implementation (JavaScript)

```javascript
// `transfer` is one entry of the `transfers` array in the /v2/tx/status response.
// Returns 'success', 'pending', 'failed', or 'not_started' for each step.
function getStepStatuses(transfer) {
  const succeeded = transfer.state === 'STATE_COMPLETED_SUCCESS';
  const failed = transfer.state === 'STATE_COMPLETED_ERROR' || transfer.state === 'STATE_PENDING_ERROR';
  const abandoned = transfer.state === 'STATE_ABANDONED';
  const blockingIndex = transfer.next_blocking_transfer?.transfer_sequence_index;
  const lastIndex = transfer.transfer_sequence.length - 1;

  return transfer.transfer_sequence.map((_, index) => {
    if (succeeded) return 'success';
    if (blockingIndex === undefined) {
      return failed && index === lastIndex ? 'failed' : 'success';
    }
    if (index < blockingIndex) return 'success';
    if (index > blockingIndex) return 'not_started';
    return failed || abandoned ? 'failed' : 'pending';
  });
}
```

Use the returned statuses to style each step in your UI, for example its color, icon, or loading animation.

## Understanding Asset Release (`transfer_asset_release`)

The `transfer_asset_release` object shows where the user's assets have ultimately landed or are expected to be claimable, especially in scenarios involving swaps or complex routes.

| Field | Description |
|---|---|
| `chain_id` | The chain ID where the assets are located. |
| `denom` | The denomination (asset identifier) of the released assets. |
| `amount` | The quantity of the released assets. |
| `released` | Whether the assets have been released to the user (e.g., available in their wallet or claimable). If `false`, it might indicate that assets are still in a contract or awaiting a final step for release. |

When a cross-chain swap fails, use `transfer_asset_release` to find where the user's funds are. For how assets are handled in different failure scenarios, see [Handling Cross-Chain Failure Cases](./handling-cross-chain-failure-cases.mdx).
