When a cross-chain transfer or swap fails, where the user's funds end up depends on where it failed. Find the case in the table below, then see its section for details.

## Where Funds End Up

| Failure | Where the user's funds end up |
|---|---|
| [IBC pre-swap or swap failure](#pre-swap-or-swap-failures) | The original tokens, back at the user's address on the source chain |
| [IBC post-swap failure](#post-swap-failures) | The destination asset, at the user's address on the swap chain |
| [Axelar swap failure](#axelar-failures) | The Axelar-transferred token, at the user's recovery address on the swap chain |
| [CCTP attestation outage or blocklisted recipient](#cctp-failures) | Burned on the source chain and inaccessible until the issue is resolved |
| [Hyperlane validator threshold not met](#hyperlane-failures) | Inaccessible on both chains until the threshold is met, then delivered on the destination chain |
| [Go Fast timeout](#go-fast-failures) | Refunded in full, including fees, on the source chain |

## IBC Transfers and Swaps

An IBC route can fail before or during the swap, or after the swap. The examples below use a route where the source asset is ATOM on Neutron, the destination asset is STRIDE on Stride, and the swap takes place on Osmosis.

### Pre-swap or swap failures

**What happens:** One of the ICS-20 transfers leading up to the swap fails, or the swap itself fails (usually due to slippage).

**Where the funds end up:** The user's original source tokens are returned to their starting address on the source chain.

**Common causes:**
* Inactive relayers on a channel allow a packet to time out
* Slippage: the amount out for the swap is less than the user's specified minimum
* The user or frontend provides an invalid recovery address
* An IBC client on the destination chain has expired

**Examples:**
* The tokens transfer from Neutron to the Hub to Osmosis. The swap starts, but the price of STRIDE has risen so much that the swap exceeds slippage tolerance and fails. Error acks propagate back to the Hub and then Neutron, releasing the user's ATOM to their address on Neutron.
* The transfer from Neutron to the Hub isn't picked up by a relayer for more than 5 minutes (past the `timeout_timestamp`). When a relayer comes online, it relays a timeout message to Neutron, releasing the user's ATOM back to their address on Neutron.

This is the only kind of failure that can happen on a route that contains only transfers. Either the tokens reach the destination chain, or the user ends up with the same tokens on the chain where they started.

### Post-swap failures

**What happens:** One of the transfers from the swap chain to the destination chain fails, after the user's tokens have already been swapped for the destination asset.

**Where the funds end up:** The destination asset is sent to the user's address on the swap chain. This is the address you pass in `address_list` to `/v2/fungible/msgs` for the chain where the swap takes place. That chain is the `chain_id` of the venue in `swap_venues` in the `/v2/fungible/route` response.

**Common causes:**
* Inactive relayers on a channel allow a packet to time out
* The user or frontend provides an invalid address for the destination chain
* An IBC client on the destination chain has expired

**Example:** The swap succeeds and the transfer to Stride starts, but the relayer between Osmosis and Stride is down, so the packet times out after 5 minutes. When the relayer comes back online 8 minutes later, it relays a timeout message to Osmosis, releasing the user's STRIDE to their Osmosis address.

<Frame caption="Post-swap failure: the user ends up with STRIDE on Osmosis">![In a post-swap error, the user will end up with their destination asset tokens in their address on the chain where the swap took place (e.g. STRIDE on Osmosis in this example)](/images/5c93590-error-type-2.png)</Frame>

<Warning>
 **Failures might occur for each transaction in a multi-tx sequence**

 In a multi-tx route, each transaction can fail in the ways described on this page. So tokens may end up on any chain where a transaction starts, not only on the initial chain or the swap chain.

 For example, if a pre-swap failure happens in the second transaction, the tokens end up on the chain that the second transaction started from. In the IBC example above, suppose the Neutron to Hub transfer and the Hub to Osmosis transfer are separate user transactions. If the first succeeds and the swap in the second exceeds maximum slippage, the ATOM ends up in the user's account on the Hub.
</Warning>

## Axelar Failures

Axelar transfers can be tracked on [Axelarscan](https://axelarscan.io/). Axelar's relayer or execution services often delay Axelar transfers. If a transaction is taking longer than expected, users can find it on Axelarscan and manually execute the steps needed to complete the transfer. See the [Axelar docs](https://docs.axelar.dev/gmp/track-and-recover/recover-transactions) for how to use Axelarscan.

The Skip Go API may use Axelar's General Message Passing (GMP) to move assets between EVM and Cosmos. Axelar has similar failure modes to IBC.

### Swap failures

**What happens:** Axelar GMP moves the user's assets from an EVM chain to the swap chain, and then the swap fails due to a timeout or slippage.

**Where the funds end up:** The user receives the Axelar-transferred token at their recovery address on the swap chain. This is different from an IBC swap failure, where the user gets their tokens back on the source chain.

**Common causes:**
* Slow relaying from Axelar causes a timeout, so the swap is not attempted
* Slippage: the amount out for the swap is less than the user's specified minimum

### Post-swap failures

Once the swap is executed, Axelar is no longer involved, so the [IBC post-swap failures](#post-swap-failures) section applies.

## CCTP Failures

Routes that use CCTP rely on Circle to produce attestations. Circle's attestation service waits for a number of block confirmations on the source chain before producing an attestation. See [Circle's documentation](https://developers.circle.com/cctp/concepts/finality-and-block-confirmations) for the number of confirmations required.

**Attestation service outage:** If Circle's attestation service has an outage, malfunctions, or becomes unresponsive, CCTP transfers still burn assets on the source chain but cannot mint them on the destination chain. The burned funds are inaccessible until the attestation service recovers.

**Blocklisted recipient:** If the recipient address on the destination chain is blocklisted by Circle, the burn on the source chain succeeds but the USDC mint on the destination chain fails. The funds stay inaccessible until Circle removes the address from the blocklist. After that, the mint can be completed. CCTP V2 attestations expire after 24 hours, so a new attestation must be requested from Circle first. If this happens, open a ticket in the [Interchain Discord](https://discord.com/invite/interchain).

## Hyperlane Failures

Each Hyperlane token transfer route is secured by an Interchain Security Module (ISM), chosen by the deployer of the route's Hyperlane Warp Route contracts (the interface for sending tokens across chains with Hyperlane). The ISM defines what a message needs in order to be processed on the destination chain.

The most common ISM is a Multisig ISM, where the route's validators sign attestations that a message on the origin chain is valid. If not enough validators have signed to reach the threshold, the user cannot access the funds on either chain. Once enough validators sign, Hyperlane delivers the funds to the user on the destination chain. Other ISMs work the same way with their own requirements. See the [Hyperlane documentation](https://docs.hyperlane.xyz/docs/protocol/ISM/modular-security) for the types of ISMs.

## Go Fast Failures

If no solver fills a user's intent (a transfer order that solvers fill) within a set time, the transfer times out and the user is refunded, so they do not lose funds.

1. **Intent expiration:** When a user submits an intent by calling `submitOrder` on the source chain, a time limit is set. Solvers monitor the intent and decide whether they can fill it within that time. If no solver fills it before the timeout, the refund process begins.
2. **Refund:** After the timeout, the solver calls `initiateTimeout` on the Go Fast contract on the destination chain (anyone can call it). A Hyperlane message then refunds the user on the source chain. The refund is the full amount the user sent, including the fee for solver compensation.
